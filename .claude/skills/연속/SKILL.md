# 연속

번호 붙은 작업 목록을 **1번부터 순서대로, 끝까지, 안 멈추고** 처리한다.

## 세 가지 규칙

### a. 결정은 스스로 한다 — 질문하지 않는다

작업 도중 갈림길이 생겨도 사용자에게 묻지 않는다. 깊게 생각해서 가장 적절한 쪽을 고르고 진행한다.

- `AskUserQuestion` 을 쓰지 않는다.
- "A 로 할까요 B 로 할까요?" 로 턴을 끝내지 않는다.
- 고른 근거는 **일이 끝난 뒤** 최종 보고에 한 줄로 적는다. 진행 중에 설명하려고 멈추지 않는다.
- 정말로 되돌릴 수 없고 위험한 일(데이터 삭제, 외부 발송, 강제 push)만 예외다. 그 항목은 **건너뛰고 나머지를 끝낸 뒤** 왜 건너뛰었는지 보고한다 — 거기서 전체를 멈추지 않는다.

### b. 중간에 들어온 질문은 받아만 놓는다

작업 중 사용자가 새 메시지를 보내도 **큐의 순서를 바꾸지 않는다**.

- 새로 들어온 번호는 **큐의 맨 뒤**에 붙인다. 방금 받았다고 먼저 하지 않는다.
- 질문이 들어오면 답을 **메모해 두고** 하던 번호를 계속한다. 답은 그 번호를 끝낸 뒤 한다.
- 예외 하나: 이미 **끝낸 번호에 대한 수정 요청**은 그 자리에서 즉시 반영한다. 새 일이 아니라 앞선 일의 마무리이기 때문이다.
- 지금 하는 일을 아예 뒤집는 지시("그거 하지 마", "되돌려")는 즉시 따른다.

### c. 처음부터 끝까지 마무리한다

- 목록의 **모든** 번호를 끝낸다. 남은 게 있는 채로 턴을 끝내지 않는다.
- "여기까지 하고 확인받겠습니다" 로 끊지 않는다.
- 중간 보고를 하려고 멈추지 않는다. 보고는 마지막에 한 번.
- 한 항목이 막히면 그 항목만 남기고 **나머지를 전부** 끝낸 뒤, 무엇을 왜 못 했는지 보고한다.

## 진행 방식

1. 받은 목록을 번호대로 정리한다. 번호가 없으면 순서대로 번호를 매긴다.
2. `TaskCreate` 로 항목마다 하나씩 등록한다 — 사용자가 어디까지 왔는지 볼 수 있게.
3. 1번부터 처리한다. 각 항목마다:
   - 고쳐야 할 파일을 찾아 고친다.
   - 그 항목이 끝나면 `TaskUpdate` 로 완료 표시.
4. 전부 끝나면 검증을 **한 번에** 돌린다:
   - `npx tsc --noEmit -p tsconfig.app.json` — 맨 `npx tsc --noEmit` 은 루트 tsconfig 의 `files: []` 때문에 항상 통과하므로 쓰지 않는다.
   - `npx eslint <바꾼 파일들>`
   - `npm run build`
5. 커밋한다. 항목이 서로 다른 주제면 주제별로 나눠 커밋한다.
6. 마지막에 한 번 보고한다 — 번호마다 무엇을 했고, 갈림길에서 무엇을 왜 골랐는지.

## 보고 형식

```
1. <한 일> — <고른 근거가 있으면 한 줄>
2. <한 일>
...
N. 못 함 — <이유>
```
